# GAMS 项目 Bug 审查报告

- 审查日期：2026-08-01
- 审查分支：`main`
- 审查基线：GG 2.0.2 / `versionCode 11`
- 状态约定：`OPEN` 表示已确认、尚未修复
- 范围：V2 Android 客户端、授权 Worker、运行包 Worker、GitHub Actions、发布资料与仓库卫生

## 建议修复顺序

1. `BUG-001`：统一 V2 客户端与授权 API 协议，否则从仓库重新部署授权 Worker 后 V2 无法启动。
2. `BUG-002`：封死 WebView 内存引擎泄露路径。
3. `BUG-003`：拆分管理登录、令牌签名和运行包加密密钥。
4. `BUG-004`、`BUG-005`、`BUG-006`：修复敏感数据生命周期与生产发布链。
5. 再处理并发、超时、WebView 安全和仓库清理问题。

## BUG-001：V2 客户端与可重复部署的授权 API 协议不兼容

- 严重度：**Critical / 阻断**
- 状态：`OPEN`
- 位置：
  - `v2/android/client/src/main/java/com/jinli/ggsecure/V2LicenseManager.java`
  - `license-api/src/index.js`
  - `.github/workflows/deploy-license-api.yml`

### 现象

V2 客户端启动时会请求：

- `POST /v1/challenge`
- 带设备公钥、签名、指纹和证书摘要的 `/v1/activate`、`/v1/check`
- `POST /v1/device/unbind`

但 `license-api/src/index.js` 当前只注册旧版：

- `/v1/admin/*`
- `/v1/activate`
- `/v1/check`

其中没有 `/v1/challenge` 和 `/v1/device/unbind`，旧版激活流程也不会保存 `public_key`、`key_fingerprint`、`certificate_digest`、`session_version`。运行包 Worker 随后又要求这些字段存在。

### 影响

从当前 `main` 重新部署 `license-api` 后，V2 客户端会在首次 challenge 阶段得到 404；即使绕过 challenge，运行包 Worker 也会因为设备缺少公钥信息而返回 `device_unbound`。

### 修复

把 V2 授权协议正式合入 `license-api/src/index.js`，补齐数据库迁移，并为 challenge、激活、检查、解绑、运行包访问建立一套端到端契约测试。旧版接口应明确版本隔离，不要由两套不兼容客户端共用同一路径却使用不同请求结构。

## BUG-002：任意外部网页可从特权 WebView 读取内存中的 `game.js`

- 严重度：**Critical / 阻断**
- 状态：`OPEN`
- 位置：`v2/android/client/src/main/java/com/jinli/ggsecure/MainActivity.java`
- 涉及函数：`shouldInterceptRequest`、`memoryGameResponse`、`isEngineRequest`、`shouldOverrideUrlLoading`

### 原因

1. 所有 HTTP/HTTPS 地址都允许继续在同一个 WebView 内打开。
2. `isEngineRequest()` 对两个地址使用 `contains()` 子串判断，而不是精确校验 scheme、host、port、path。
3. 命中后直接返回内存中的完整 `game.js`。
4. 返回头包含 `Access-Control-Allow-Origin: *`。

攻击页面只需在 URL 路径或查询参数中构造包含 `space-z.ai/game.js` 或 Worker 引擎地址的字符串，就可能触发本地拦截并读取响应，再上传到外部服务器。

### 影响

绕过“APK 内不保存核心 JS”的保护目标，完整导出已解密引擎代码。

### 修复

- 使用 `Uri` 精确匹配固定 scheme、host 和 path，禁止字符串 `contains()`。
- 删除通配 CORS。
- 特权 WebView 只允许 `m.66rpg.com`、`www.66rpg.com` 和受控虚拟资源域。
- 外部网页必须交给系统浏览器打开，不能继续运行在已注入控制脚本、可访问内存资源的 WebView 中。
- 更稳妥的方案是使用 `WebViewAssetLoader` 或受控本地域承载内存资源。

## BUG-003：同一个管理密码同时保护三类高价值资产

- 严重度：**Critical / 阻断**
- 状态：`OPEN`
- 位置：
  - `license-api/src/index.js`
  - `v2/runtime/src/index.js`
  - `.github/workflows/deploy-license-api.yml`
  - `.github/workflows/v2-deploy-runtime.yml`

### 原因

`LICENSE_ADMIN_PASSWORD` 被同时用于：

1. 管理端明文密码登录校验；
2. 管理令牌和用户会话令牌的 HMAC 签名；
3. V2 运行包内容密钥的主密钥派生。

### 影响

任何一次管理密码泄露，不仅能登录管理端，还能离线伪造任意 admin/session token，并解密运行包内容密钥。管理操作、授权系统和核心代码保护会同时失守。

### 修复

至少拆成三个独立、随机生成的 Secret：

- `ADMIN_LOGIN_SECRET`
- `TOKEN_SIGNING_SECRET`
- `RUNTIME_MASTER_KEY`

运行包主密钥应为高熵随机字节，不应从人类可输入密码派生。完成密钥轮换，并让旧 token 立即失效。

## BUG-004：强制更新路径丢弃已解密运行包但没有清零

- 严重度：**High**
- 状态：`OPEN`
- 位置：`V2LicenseManager.RuntimeResult.valid()`

### 原因

客户端先调用 `loadRuntime()` 下载并解密 `RuntimePayload`，之后才判断是否强制更新。强制更新时返回 `payload = null`，但没有调用 `payload.wipe()`。

### 影响

完整 `noname.js` 和 `game.js` 会继续留在 Java 堆中直到 GC；界面已经拿不到引用，无法主动清零。同时产生无意义的下载和解密开销。

### 修复

在下载运行包之前判断 `forceUpdate`；或者在返回强制更新结果前明确调用 `payload.wipe()`。

## BUG-005：Pull Request 会直接执行生产授权 Worker 部署

- 严重度：**High**
- 状态：`OPEN`
- 位置：`.github/workflows/deploy-license-api.yml`

### 原因

生产部署 workflow 同时监听 `push` 和 `pull_request`，而 PR 事件没有仅测试、不部署的分支判断。

### 影响

同仓库分支创建 PR 时，尚未合并、尚未审核的代码可能直接部署到生产 Worker。一次测试 PR 就能覆盖线上授权服务。

### 修复

- 生产部署只允许受保护 `main` 的 `push` 或带环境审批的 `workflow_dispatch`。
- PR 只运行 lint、单元测试、迁移检查和本地 Wrangler dry-run。
- 使用 GitHub Environment 审批和最小权限 Secret。

## BUG-006：发布链只测试旧版授权协议，无法发现 V2 已经不兼容

- 严重度：**High**
- 状态：`OPEN`
- 位置：
  - `.github/workflows/deploy-license-api.yml`
  - `.github/workflows/v2-build-apks.yml`

### 现象

授权 API smoke test 仍使用旧版无签名请求，`appVersion: 5`；正式客户端为 `versionCode 11`，使用 challenge、设备签名、公钥绑定和解绑接口。APK 构建只验证包名、版本、签名状态和少数明文标记，不验证真实启动链路。

### 影响

CI 全绿也不能证明正式 V2 能激活、检查、下载运行包或解绑设备，正是 `BUG-001` 未被发现的原因。

### 修复

增加真实 V2 生命周期测试：创建卡密 → challenge → 签名激活 → check → runtime challenge/access/bundle → 解绑 → 旧 token 失效 → 强制更新。

## BUG-007：设备数量限制存在并发穿透

- 严重度：**High**
- 状态：`OPEN`
- 位置：`license-api/src/index.js` 的 `activate()`

### 原因

新设备激活采用：

1. 查询当前有效设备数；
2. 判断是否达到 `max_devices`；
3. 单独插入设备。

这不是原子事务。两个不同设备同时激活时，都可能看到旧计数并都成功插入。

### 影响

一机一码或限定设备数的商业规则可被并发请求绕过。

### 修复

在数据库层建立原子约束。可使用 D1 transaction/原子条件写入、按许可证维护绑定计数，或在单条 SQL 中完成“未超限才插入”。并增加并发激活测试。

## BUG-008：仓库提交了大量 Android `build/` 产物且缺少根 `.gitignore`

- 严重度：**High**
- 状态：`OPEN`
- 位置：`v2/android/client/build/**`

### 现象

仓库中存在 `.class`、`.dex`、lint cache、merged resources、APK 中间文件、绝对 CI 路径等大量生成物，根目录没有 `.gitignore`。

### 影响

- 仓库体积持续膨胀；
- 代码审查被生成文件淹没；
- 旧构建结果可能被误当作当前结果；
- 泄露 CI 目录结构；
- 合并冲突和提交噪音显著增加。

### 修复

添加根 `.gitignore`，至少忽略：

```gitignore
.gradle/
**/build/
local.properties
*.apk
*.aab
*.jks
*.keystore
```

随后执行 `git rm -r --cached v2/android/client/build`。若仓库体积仍过大，再使用历史清理工具移除旧二进制。

## BUG-009：特权 WebView 允许任意站点导航和任意自定义 Scheme

- 严重度：**High**
- 状态：`OPEN`
- 位置：`MainActivity.shouldOverrideUrlLoading()`

### 原因

- 所有 `http`、`https` 返回 `false`，继续在当前 WebView 打开；
- 其他任意 scheme 直接传给 `Intent.ACTION_VIEW`；
- 没有域名白名单、scheme 白名单或用户确认。

### 影响

钓鱼页面可以在拥有控制脚本和内存资源能力的 WebView 中运行；恶意链接还可尝试拉起外部应用、深链或 intent 处理器。

### 修复

仅允许明确的站点白名单留在 WebView。外部 HTTPS 使用系统浏览器；拒绝 `file:`、`content:`、`javascript:`、`intent:` 等未明确允许的 scheme。

## BUG-010：网络多通道回退最坏可能让启动卡住数分钟

- 严重度：**High**
- 状态：`OPEN`
- 位置：
  - `RuntimeTransport.requestAcrossChannels()`
  - `ResilientApiTransport.post()`

### 原因

多个域名、多个公共 DNS 和最多 12 个 IP 地址按顺序尝试，每次有独立连接和读取超时，没有总截止时间，也没有取消信号。

### 影响

网络异常、DNS 污染或黑洞 IP 下，界面可长期停留在“正在启动”，用户无法判断是死机还是仍在重试。

### 修复

增加全局 deadline，例如 20～30 秒；并行或 Happy Eyeballs 尝试；限制 IP 数量；生命周期结束时取消请求；向 UI 返回明确的当前阶段和重试按钮。

## BUG-011：服务器返回的 `bundlePath` 未校验就进入手写 HTTP 请求行

- 严重度：**Medium**
- 状态：`OPEN`
- 位置：
  - `V2LicenseManager.loadRuntime()`
  - `RuntimeTransport.directTlsRequest()`

### 原因

`bundlePath` 来自 JSON 响应，随后直接拼接到：

```text
GET <bundlePath> HTTP/1.1
```

没有禁止 CR/LF、绝对 URL、空格或非 `/` 开头路径。

### 影响

服务端配置错误或被攻陷时，可造成请求行/请求头注入，或者让 Bearer token 被发送到意外路径。

### 修复

只接受以 `/v2/runtime/bundle?` 开头的相对路径，拒绝 CR、LF、空格和绝对 URL。更好的是客户端自行根据已签名版本构造固定路径，不信任响应中的任意路径。

## BUG-012：WebView 开启混合内容和第三方 Cookie

- 严重度：**Medium**
- 状态：`OPEN`
- 位置：`MainActivity.configureWebView()`

### 原因

使用：

- `MIXED_CONTENT_COMPATIBILITY_MODE`
- `setAcceptThirdPartyCookies(webView, true)`

### 影响

HTTPS 页面可加载不安全 HTTP 子资源，增加中间人注入面；第三方 Cookie 扩大跨站跟踪和会话泄露风险。

### 修复

改为 `MIXED_CONTENT_NEVER_ALLOW`，默认关闭第三方 Cookie，只对确有业务需要的最小场景单独放行。

## BUG-013：WebView 状态恢复失败时会停在空白页

- 严重度：**Medium**
- 状态：`OPEN`
- 位置：`MainActivity.showBrowser()`

### 原因

只要 `savedInstanceState != null` 就调用 `restoreState()`，但忽略其返回值；恢复失败后不会执行 `loadUrl(START_URL)`。

### 影响

进程重建、WebView 版本变化或状态包损坏时可能出现白屏。

### 修复

```java
if (savedInstanceState == null || webView.restoreState(savedInstanceState) == null) {
    webView.loadUrl(START_URL);
}
```

## BUG-014：清零运行包与 WebView 读取流之间存在竞态

- 严重度：**Medium**
- 状态：`OPEN`
- 位置：
  - `RuntimePayload.openGameStream()`
  - `RuntimePayload.wipe()`
  - `MainActivity.releaseRuntime()`

### 原因

`openGameStream()` 返回直接引用内部 `game` 数组的 `ByteArrayInputStream`。锁只保护“创建流”这一瞬间；之后 `wipe()` 可以在 WebView 仍读取时把同一数组全部置零。

### 影响

后台恢复、重载或销毁竞态下，脚本响应可能被截断或变成零字节，表现为随机黑屏、脚本语法错误或功能缺失。

### 修复

采用带引用计数的只读流，所有流关闭后再清零；或者在停止并确认 WebView 请求结束后再擦除。不要在仍可能有读取者时修改底层数组。

## BUG-015：敏感脚本转换为不可清零的 Java `String`

- 严重度：**Medium**
- 状态：`OPEN`
- 位置：
  - `RuntimePayload.nonameSource()`
  - `MainActivity.wrapControlScript()`

### 原因

`noname.js` 从可清零的 `byte[]` 转为不可变 `String`，之后又通过字符串拼接生成第二份脚本字符串。`wipe()` 只能擦除原数组，不能清除这些 String。

### 影响

控制脚本可能在 Java 堆中保留较长时间，内存擦除承诺不完整，增加内存转储提取风险。

### 修复

减少复制和字符串生命周期；使用短生命周期字符缓冲并及时解除引用。由于 WebView 注入 API 最终需要 String，应在安全模型中明确该残余风险，不要把 `byte[] wipe()` 等同于完整清除。

## BUG-016：安全存储发生任意读取异常时会永久删除授权状态

- 严重度：**Medium**
- 状态：`OPEN`
- 位置：`SecureStore.loadState()`

### 原因

解密、AndroidKeyStore、Base64 或 JSON 任意异常都会立即执行：

```java
preferences.edit().remove(PREF_BLOB).commit();
```

### 影响

一次暂时性的 KeyStore/系统异常也会把卡密和 token 永久清除，用户被迫重新激活；错误原因也被完全吞掉，难以诊断。

### 修复

区分“数据确定损坏”和“系统暂时不可用”。先保留原 blob、记录安全的错误码并允许重试；只有认证标签明确失败或格式永久不兼容时才进入受控恢复流程。

## BUG-017：请求体上限按 UTF-16 字符数计算，可被多字节内容绕过

- 严重度：**Medium**
- 状态：`OPEN`
- 位置：
  - `license-api/src/index.js` 的 `readJson()`
  - `v2/runtime/src/index.js` 的 `readJson()`

### 原因

无 `Content-Length` 或分块请求时，代码使用 `text.length` 判断大小。JavaScript 字符数不等于 UTF-8 字节数，中文或 emoji 可让实际字节数远大于限制。

### 影响

攻击者可提交超出设计上限的请求体，增加 Worker 内存和 CPU 消耗。

### 修复

读取 `ArrayBuffer` 后按 `byteLength` 限制，再解码 JSON；同时保持平台级请求大小限制。

## BUG-018：授权与运行包限流均存在并发竞态

- 严重度：**Medium**
- 状态：`OPEN`
- 位置：两个 Worker 的 `allowRate()`

### 原因

限流采用独立的 `SELECT` → 判断 → `UPDATE`。多个并发请求可读取同一个旧计数并全部通过。

### 影响

登录爆破、激活、challenge、运行包下载等接口在并发下可超过配置阈值。

### 修复

使用 Durable Object、原子 UPSERT/条件 UPDATE，或专门的 Cloudflare Rate Limiting。增加并发测试，不只测试串行请求。

---

## BUG-019：文件选择回调在 WebView 销毁时未取消

- 严重度：**Medium**
- 状态：`OPEN`
- 位置：`MainActivity.destroyWebView()`、`onDestroy()`

### 原因

`fileChooserCallback` 只在新选择器覆盖或收到 `onActivityResult` 时清空，销毁页面时没有发送 `null` 并释放。

### 影响

可能保留旧 Activity/WebView 引用；用户稍后返回文件结果时会投递给已销毁页面，造成泄漏、无响应或异常状态。

### 修复

销毁时执行 `fileChooserCallback.onReceiveValue(null)` 并置空，同时使用 Activity Result API 管理生命周期。

## BUG-020：下载文件没有可信文件名、扩展名和来源限制

- 严重度：**Low**
- 状态：`OPEN`
- 位置：`MainActivity.createDownloadListener()`

### 原因

所有下载都命名为 `download_<timestamp>`，不保留扩展名，也不校验 URL scheme、host 和 MIME；下载服务对象还直接强制转换，未先判空。

### 影响

下载后的 APK、ZIP、图片等可能难以打开；恶意页面可触发任意来源下载，用户只看到笼统“已开始下载”。

### 修复

使用 `URLUtil.guessFileName()`，清洗文件名，限制 HTTPS 和可信域，展示来源、类型、大小并要求确认；判空 `DownloadManager`。

## BUG-021：V2 发布文档仍停留在 2.0.0

- 严重度：**Low**
- 状态：`OPEN`
- 位置：`v2/README.md`

### 现象

文档写的是 `2.0.0 / versionCode 9`，当前构建配置和正式发布链已经是 `2.0.2 / versionCode 11`。

### 影响

维护人员可能使用错误版本号、错误验收标准或错误发布说明，增加回滚和签名操作失误概率。

### 修复

让发布 workflow 自动生成或校验 README 中的当前版本信息，避免手工同步。
