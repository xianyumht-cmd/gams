## 已确认且尚未修复的实际 Bug

### Runtime 密钥迁移与发布链不兼容

当前代码同时存在以下不一致：

- `v2/runtime/release/manifest.json` 的 `keyCipher` 使用旧算法：
  `SHA-256("gg-v2-runtime-master:" + LICENSE_ADMIN_PASSWORD)`。
- 新 Runtime Worker 直接使用独立的 32 字节 `RUNTIME_MASTER_KEY`。
- `v2/runtime/tools/build_release.py` 仍使用旧密码派生算法生成 `keyCipher`。
- `.github/workflows/v2-publish-encrypted-runtime.yml` 仍读取 `LICENSE_ADMIN_PASSWORD`，仍向 Worker 写入 `ADMIN_PASSWORD`。
- 发布工作流把 release 提交到 `v2-server-authoritative`，Runtime Worker 从 `main/v2/runtime/release/` 读取线上 manifest 和 bundle。

直接结果：

1. 使用新的独立随机 `RUNTIME_MASTER_KEY` 部署当前 Runtime Worker，现有 `2.0.2-r1` 内容密钥解密失败，接口返回 `runtime_invalid`。
2. 执行现有永久发布工作流，新 release 不会进入 Runtime Worker实际读取的 `main` 路径，并会部署旧分支中的 Worker 代码。

PR #25 在该问题修复和完整验收前保持 Draft，禁止合并。

## 完成条件

1. `build_release.py` 改为接收并严格校验原始 32 字节 `RUNTIME_MASTER_KEY`。
2. 永久发布工作流使用独立的签名密码和 Runtime 主密钥。
3. release 先进入 `main`，再由主分支部署工作流发布 Worker。
4. 现有 `2.0.2-r1` 的 `keyCipher` 使用最终 Runtime 主密钥重新封装，并重新签名 manifest。
5. 完成激活 → runtime access → 内容密钥解包 → bundle 下载 → AES-GCM 解密 → ZIP 内容校验。
